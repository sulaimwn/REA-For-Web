## Demonstrated problem

T026's setup recipe created a system service account without a fixed UID. The
pipeline writes uploaded files mode 0600; the sandbox is always uid/gid
1000:1000. On a Linux host where the service gets another UID, Docker mounts
the inode but the non-root parser cannot read it. Windows Docker Desktop tests
did not establish the native Linux ownership contract.

Reproduced with inert bytes in a disposable Linux Docker volume: an inode owned
by UID 1001, mode 0600, returns EACCES to UID 1000. Changing only its owner to
UID 1000 allows reading, with the same mode 0600. No program was executed.
Outside-Git reproduction: `../launch-verification/t050-identity-repro.mjs`.

## What changed

- Export the existing `WORKER_USER = "1000:1000"` and use it for the unchanged
  Docker argument. Add `assertQueueIdentity()`, which checks the effective UID
  on Linux because that determines new private file ownership.
- The queue CLI calls this before creating configuration/queue connections.
  The hosted preflight calls the same guard and reports an actionable,
  sanitized Linux queue identity stage. It does not change API admission or
  claim that a separately running website cannot enqueue while the worker is off.
- Correct the account recipe to require UID 1000. Existing UID-1000 accounts
  must be resolved/configured on the dedicated host; never duplicate a UID or
  renumber an account. Its primary GID need not equal 1000; mode 0600 reads
  depend on owner UID. The unit includes a comment explaining this requirement.
- Add `npm run test:worker-identity` and its worker-CI step. The real regression
  imports the compiled guard in processes with actual Linux UIDs, reproduces
  the unreadable inode, then checks matching UID restores access even with a
  different file GID. It uses the standard worker's pinned official Node base,
  --pull=never, a labeled disposable volume and only inert text.
- Sandbox resource limits, image selection, fixed non-root UID/GID, no-network,
  read-only root/input, capabilities, upload mode/retention, tokens, schema and
  cache semantics remain unchanged. No callback lets an upload select a user.
