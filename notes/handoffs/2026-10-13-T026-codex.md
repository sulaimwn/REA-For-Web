## What changed
- Added a provider-independent dedicated Linux deployment kit and operator guide. No server, DNS, domain, bucket, billing plan or live credentials were created.
- `Dockerfile.web` builds the existing Next app as a traced standalone image. It includes the generated demos/static assets and runs as uid 1000. `REA_NODE_DEPLOY=1` enables this build mode only; the regular Cloudflare build stays unchanged.
- Compose runs the web with a read-only root, dropped capabilities, no Docker socket or staging mount, memory/process caps and loopback-only HTTP. Redis uses a dedicated bridge, loopback host port, persisted AOF data and no eviction. Optional pinned Caddy handles public HTTPS with a 1 MB request-body cap; large uploads go straight to private R2.
- The queue remains a trusted host Node service, avoiding ambiguous container-to-host bind paths. The systemd unit restricts filesystem writes to private staging and includes a bounded startup check for Docker safety/images, staging, Redis and object-store authorization. The Docker-capable service account is explicitly administrative; analysis targets remain in the unchanged disposable offline sandbox.
- Environment examples are placeholders only. Real files belong outside Git under `/etc/rea-for-web` with root-only permissions. Compose uses raw env-file values. Web/queue R2 settings and prefix must agree; their private Redis addresses differ. Nothing is baked into browser bundles or image builds.
- Public `REA_UPLOAD_ORIGIN` lets Cloudflare navigation and `/upload` link to the HTTPS analysis site. Rejects credentials, query/fragment secrets, arbitrary paths and non-HTTPS schemes. No API proxy, new JSON fields, shared schema change or job-token transfer. The analysis site hosts its own job explorer/session.
- Added isolated `npm run test:hosted`: builds host queue code, starts a unique disposable Compose project, verifies web restrictions/Redis persistence/startup, runs the existing four-kind real HTTP suite and checks raw/staging cleanup. Its volume deletion is confined to the generated test project; its recursive directory deletion checks the resolved workspace parent. Normal upload data is untouched.
- Updated deployment, support and rollback docs. Analysis concurrency/CPU/RAM/deadlines are unchanged. No speculative speed settings; Claude owns the real Obsidian timing run.

## Not done / known issues
- No Linux host or private R2 bucket is confirmed. The human only knows they have a Cloudflare account; they asked what a Linux server means. Explained it is the online machine that performs analysis while their PC is off. Do not assume they agreed to a hosting purchase or cloud billing setup.
- Live R2 signing/upload/CORS/deletion, DNS/public HTTPS and actual systemd installation remain operator checks. The packaged test uses private local objects and the Windows host queue with a real Linux Docker engine, not a production Linux service manager. It does not prove production credentials/network policy.
- Caddy needs a hostname the operator controls or provider HTTPS termination. The existing workers.dev frontend remains available and cannot be pointed at this host with ordinary DNS.
- A single shared private-beta key and the existing 100-ticket/day quota remain. Public anonymous uploads need a separate admission/auth design. Cached results still require verified fresh file possession.
- The initial kit budgets service memory but does not tune throughput. Keep Claude's measured Obsidian timing separate from synthetic fixture timings. Neither is a production performance guarantee.
- The web image and R2/Redis capabilities require coordinated web/worker versions. Never roll an ASAR-only worker back into a queue containing program/APK jobs. Preserve data and prefixes through upgrades; force-killed jobs can leave containers until their own deadline.
