## What changed

T050 guards the production queue, but the local helper previously reached data
creation, package/image builds and Redis startup before launching that queue.
The hosted test also created its temporary deployment and services before the
queue guard. Both eventually fail for a native Linux effective UID other than
1000. They now check ownership at entry, before their filesystem/service work.

- Moved the existing constant and effective-UID guard into the dependency-free
  `apps/worker/src/queue-identity.ts`. `limits.ts` re-exports the same names;
  the actual container user remains 1000:1000.
- The two setup scripts import that source directly so the local helper can
  reject a mismatched user even before its first build. Their supported Node
  engines already include native erasable-TypeScript loading ([Node docs](https://nodejs.org/docs/latest-v22.x/api/typescript.html)).
  The compiled worker continues to import JavaScript normally.
- Extended the existing real Linux ownership check with both actual setup
  entrypoints, using UID 1001 in offline containers with a read-only filesystem,
  no installed dependencies, credentials or Docker socket. They must report the
  identity error instead of touching the workspace or trying to build/start.
- Documented the Linux local-mode requirement and linked the existing account
  instructions. Do not renumber users or relax private upload permissions.

## Demonstration and checks

`dev-uploads.mjs` failed at `mkdir /src/.pipeline-data` (ENOENT in the
read-only Docker Desktop bind), and the hosted script reached `mkdtemp`
(EROFS). Neither reported the wrong identity. Afterward, the same entrypoints
report the correct UID requirement first.
