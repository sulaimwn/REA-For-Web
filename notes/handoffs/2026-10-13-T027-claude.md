# T027 — Analysis speed (claude)

**Branch:** `claude/T027-analysis-speed` (create it from main in worktree `rea-web-claude-T027`)
**Status:** in progress. Plan only so far; this note is the resume point for the hourly loop.

## Facts measured on 2026-10-13
- Obsidian `obsidian.asar` (27 MB, 38 JS files) through the local upload stack:
  - transfer under 1 s;
  - queue 0.01 s;
  - **REA analysis 458 s** in the 1-CPU sandbox.
- The same analysis on the 8-core host with no sandbox took 774 s, so it isn't CPU-bound. REA parses files one at a time.
- Slow files (from REA progress): `app.js` ~60 s, `i18n.js` ~50 s, `lib/mermaid.min.js` ~54 s, `lib/defuddle.full.js` ~28 s, plus `pdfjs/*` and `codemirror/*`.
- The worker passes `--analysis-timeout-ms` = `sourceTimeoutMs` (default 180 000 ms per file).

## Findings, 11:20
- **A per-file cap can't skip a slow library.** REA's `--analysis-timeout-ms` is per source file, but its help says that on timeout it "return[s] collected partial Evidence and stop[s] the analysis". So a lower cap ends the whole run and loses every later file. REA 6.4.0 has no other controls (only `max_heap_mb` and `analysis_timeout_ms`), so there's no skip list or size limit. **Plan step 1 is dropped.**
- **Neither heap nor cores help.** Obsidian's `lib/mermaid.min.js` (2.96 MB) alone, in the worker image:

  | Setting | Time |
  |---|---|
  | 1 CPU, heap 1024 MB | 40 s |
  | 1 CPU, heap 3072 MB | 37 s |
  | 4 CPUs | 34 s |

  REA's per-file analysis is effectively single-threaded.
- **What's left:**
  - (a) caching and pre-analysis, so popular apps are instant;
  - (b) more concurrent jobs on a multi-core host, which raises throughput, not one job's latency;
  - (c) sharding one app across parallel REA runs. This loses REA's whole-app correlation (IPC pairing, cross-file imports), so it's not recommended.
  - (d) an upstream REA request: a "skip this file and continue" timeout mode, or a size/pattern skip list.

## Original plan (step 1 superseded by the findings above)
1. **Per-file cap experiment.** Run the CLI or worker on Obsidian and GitHub Desktop with `sourceTimeoutMs` at 180 s (now), 60 s and 30 s. Record for each:
   - total time;
   - nodes and edges;
   - `filesWithAnalysisIssues`;
   - which files lost detail;
   - IPC, bridge and process counts. These are the facts users care about.

   Pick the lowest cap that keeps the architectural findings. Only then propose a default change to Codex, since it's a worker setting.
2. **Pre-analyzed popular apps.** A script runs the CLI on locally installed apps and stores the results as demos or a "popular apps" cache, so visitors get instant maps. Locally available: GitHub Desktop, VS Code, Obsidian. Others would need downloads: ask the human first.
3. **Wait-time estimate in the job UI.** Codex owns the upload UI; coordinate before editing it.
