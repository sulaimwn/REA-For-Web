## What changed
- Reproduced a cleanup hang: BullMQ's worker Redis connection retries indefinitely. An unresolved `job.updateProgress()` kept the processor's `finally` block waiting forever, even after analysis finished or failed. Both regression cases timed out against the original implementation.
- Bound each serialized progress write to five seconds. A write failure still prevents result publication, and later queued progress callbacks do not submit more writes after that failure. Analysis failures retain their original sanitized error; a successful analysis whose progress cannot be saved fails with the sanitized `progress_unavailable` reason.
- The job status endpoint translates that reason to an understandable queue-connection/re-upload message. No new API fields, schema changes, dependencies or cache revision.
- Added an actual Redis write-stall regression to the dedicated integration suite. It pauses writes on that suite's dedicated Redis only, checks raw/staging cleanup before writes resume, verifies no result is published, then checks that another job succeeds after recovery.

## Not done / known issues
- A timeout cannot cancel an already-issued Redis command. Its late completion/rejection stays observed, and the backlog is not submitted. A late progress update can become visible after recovery, but it cannot publish a project or overwrite terminal job state.
- The five-second bound covers each progress **write**, not REA analysis. If analysis is still running when a progress write stalls, cleanup occurs after analysis finishes/fails under the existing deadline. This change does not abort REA early.
- BullMQ cannot save terminal state or release the global slot while Redis remains unavailable. Those operations resume when Redis is reachable; the fix prevents that outage from also retaining raw/staging data after analysis returns. A short write stall may now cause an otherwise completed analysis to fail; retaining the existing no-publication-on-progress-failure rule is intentional.
