# T052 — R2 response-body deadlines (Codex)

**Branch:** `codex/T052-r2-body-deadline`
**Implementation:** `4c16106`
**Status:** review; source not merged

## Demonstrated bug

T036's request timer and the installed Smithy HTTP-handler timers are cleared
when a GET returns headers, before its body finishes. The processor has a
separate 60-second pipeline timeout, but the authorized project-download route
streams the returned body through `Readable.toWeb` without another deadline.
A stalled private result could leave its viewer waiting indefinitely.

Reproduced with the actual S3 SDK, a loopback-only HTTP service and inert bytes.
The server sent Content-Length and a partial body, then stopped. The store's
150 ms deadline did not stop consumption; it ran for **1,237 ms**, until the
probe's independent 1,200 ms safety timer destroyed the stream (ECONNRESET).
The client used `throwOnRequestTimeout: true`, as production does. Inspection
of the installed HTTP handler also showed its timeouts clearing at headers.
No real R2 bucket or cloud credentials were used.

## What changed

- A GET retains its original operation timer across retries, response headers
  and body consumption. Production stays at the existing **60-second** limit.
- At expiry, destroy the body with the existing sanitized
  `storage_unavailable` error, then abort the underlying HTTP request. This
  order preserves the useful classification instead of an incidental reset.
- Completion, consumer cancellation/close and errors clear the timer; HEAD,
  PUT, DELETE and LIST still clear it when those operations settle.
- Documented that a failed result read can be retried by reloading its authorized
  tab. Its private stored result is retained. A raw download failure still fails
  before analysis and goes through the existing raw/staging cleanup.
- Extended the real HTTP storage suite: headers-only stall, partial-body stall,
  same-client download recovery, the actual project route's Web-stream boundary,
  delayed headers consuming the same deadline, and processor cleanup/recovery.

- `npm run test:storage --workspace=@rea-studio/pipeline`: **10/10**, zero skipped.
  The prior request/backoff/deletion/publication checks pass alongside the new

- `npm test --workspace=@rea-studio/pipeline`: **30/30**, zero skipped.
- The original reproduction with production-like HTTP-handler settings now
  fails after **155 ms**, with `storage_unavailable`, under the same 150 ms

- Timed-out GET connections close. A later read on the same SDK client succeeds.
  Partial raw reads never run the analyzer or publish a result; raw deletion and
  staging cleanup succeed, and a subsequent complete upload publishes normally.
- Every loopback service/client and uniquely owned temporary directory from the
  checks was cleaned up. No existing servers or Docker containers were touched.
