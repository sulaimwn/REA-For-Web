## What changed
- `packages/rea-adapter/src/heuristics.ts`: `bridge-member-read` heuristic. REA records the
  `contextBridge` API (`notesApi` with members `save`, `list`, `quit`) and, in its semantic graph,
  renderer property reads (`property_path: ['notesApi', 'save']` at `renderer.js:5:8`), but never links
  them. When a read's `[apiKey, member]` matches a `bridge-api`'s key and one of its members, the adapter adds
  `<file> --calls--> <bridge-api>`, with:
  - `origin: { source: 'studio-heuristic', heuristic: 'bridge-member-read', basis: 'Reads window.notesApi.save; …' }`
  - evidence `inferred` / `medium` / authority `studio-heuristic`, located at the read site
  - `details.mechanism: 'window.notesApi.save'`
- `index.ts`: runs heuristics after REA edges are built; `AdapterReport.heuristicEdges` counts by name.
  Heuristics are add-only; REA nodes and edges are untouched.
- `rea-types.ts`: the minimal semantic-graph node shape the heuristic reads. The semantic graph is still
  not copied into StudioProject.
- `ARCHITECTURE.md`: "Studio heuristics" section.
- 4 new tests (31 total): exact links on tiny-electron (`renderer.js:5` save, `:6` list), labeling, REA edge
  count unchanged (56), no links when there's no bridge (GitHub Desktop), and unexposed members ignored.
  A mutation check (dropping the member filter) fails the last test.
- **UI** (after syncing with main, which now has T005/T011): heuristic links are drawn as a separate amber dotted
  edge labeled `(heuristic)`, never merged with REA edges, and the inspector shows a `heuristic` badge whose tooltip
  gives the basis. Checked in the browser: the `window.notesApi` neighborhood shows `preload.js --exposes-->` (REA)
  and `renderer.js --calls ×2 (heuristic)-->`. No console errors on either demo.
- **No schema changes.**

## Proposal for T012 (needs Codex's agreement; shared schema change)
REA's endpoint candidates are ~98% noise on real apps (2 of 89 real in GitHub Desktop). Proposed **optional,
backwards-compatible** field on `EndpointNode` in `packages/schema`:

```ts
/** Studio's verdict on whether this REA candidate is a real network endpoint. Absent = not assessed. */
assessment?: {
  verdict: 'plausible' | 'unlikely';
  heuristic: string;   // e.g. 'endpoint-shape'
  basis: string;       // human-readable reason
};
```

Rule (`endpoint-shape`): `plausible` if the value is an `http(s)://` / `ws(s)://` URL or `METHOD /path`, or if
the mechanism is `call:fetch` / `call:request` / `call:<x>.request` and the value starts with `/<word>`.
Otherwise `unlikely`. On the full GitHub Desktop output it keeps exactly `POST /gists` (`call:request`) and
`https://central.github.com/api/usage/desktop` (`call:fetch`) and marks the other 87 unlikely.
The UI would hide `unlikely` by default behind a "show all REA candidates" toggle. REA's own facts stay intact.
