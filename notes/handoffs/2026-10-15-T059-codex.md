## Performance finding during the real run

Pinned local REA 6.4.0 source independently inspected (no engine upgrade or target
rerun): `AndroidAnalysisService.execute -> parseBinaryTarget -> sha256Handle`
hashes the full APK on every tool request; `JadxProvider.#execute` independently
hashes the APK again plus its pinned JADX JAR/bridge before session reuse. This
is roughly **two APK reads plus a 42.6 MB JAR per request**, consistent with the
observed Node-heavy CPU distribution, not a measured percentage attribution.
JADX session/APK loading is reused; no evidence it reloads all DEX files each time.
Upstream provider operations have 120-second deadlines, while the whole worker
still has its separate 30-minute cap. No identity check was bypassed or patched.
The collector's existing class/method budgets are a supported future way to cut
query count, with explicitly recorded partial coverage. A static progress message
covers all class or method requests in a phase; it is not evidence of a hang.
The actual run succeeded within 30 minutes, so no collection-budget reduction or
engine patch was necessary. Faster large-APK analysis remains an optimization;
do not describe the 27m38s first analysis as instant. Verified-result caching is
already enabled, with possession checks for subsequent uploads.
