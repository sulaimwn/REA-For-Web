# T021 — Beyond Electron: research on every target, and .NET end to end (claude)

**Branch:** `claude/T021-beyond-electron` (from `main` @ `072b4d6`)
**Status:** review. **Includes a shared schema change: Codex, please agree (or change) before merging.**

The human said support beyond Electron is essential ("exe and everything else"). This branch:
- **researches every target REA supports** against real output (`docs/targets.md`);
- **ships .NET end to end**: schema, adapter, explorer, demo, Ask and local-mode CLI;
- documents exactly what Android, native `.exe` and websites still need.

## What changed
1. **Research: `docs/targets.md`.** REA's non-Electron graphs use the **same `JavaScriptApplicationGraph` schema** as Electron, with different node kinds, so the adapter design carries over. Per target:
   - **.NET:** works today, no extra tools.
   - **Websites:** `analyze-web-bundle` works. Tested on our own local landing page: 24 scripts parsed, Next.js/React/webpack fingerprinted. It needs a capture sandbox with egress.
   - **Android:** inventory only until a jadx-headless-mcp 0.7.1 JAR is supplied.
   - **Native .exe:** needs Ghidra 12.1 + Java. Today it fails with `provider_unavailable`.
   - **Apple:** inventory only off macOS.
2. **Real fixtures from hand-written samples with answer keys** (`fixtures/sample-apps/tiny-dotnet`, `tiny-android`):
   - A C# program built with Windows' `csc`, and a Java APK built without Gradle. Both are committed (7 KB and 13 KB); neither is ever run.
   - `fixtures/tools/target-fixtures.mjs` regenerates `tiny-dotnet.rea-6.4.0.json` and `tiny-android.rea-6.4.0.json`. Each holds unmodified REA envelopes keyed by operation, with paths scrubbed.
   - Also `reaforweb-dev-landing.web-bundle.rea-6.4.0.json`.
3. **Schema proposal (additive; existing projects unchanged)** in `packages/schema`:
   - `target.appKind` + `'dotnet'`, `target.format` + `'pe'`.
   - Node kinds:
     - `assembly` (REA artifact + assembly + module merged; references, resources, entry point, architecture)
     - `managed-type` (fields listed on the type)
     - `managed-method` (P/Invoke flag; entry point)
     - `native-import` (library!export, calling convention)
     - `external-member` (a called API outside the assembly)
   - `FINDING_CATEGORIES` is now `JAVASCRIPT_FINDING_CATEGORIES` + `DOTNET_FINDING_CATEGORIES` (`types`, `methods`, `native-imports`, `external-apis`). A project lists only its own kind's categories.
   - `EdgeDetails.callSites`, `omitted: 'managed-fields'`.
   - `STUDIO_SCHEMA_VERSION` **not bumped**: the change is additive. Codex, decide whether to bump to 0.2.0. If so, `/open` and the pipeline cache key should accept both versions.
4. **Adapter** `packages/rea-adapter/src/managed.ts`:
   - Reads REA's projection (structure) plus `inspect_managed_members.call_edges`. Those calls are REA facts the projection drops; they're kept with `origin: rea` and the members inspection's evidence.
   - `method-spec` call targets (generic instantiations REA doesn't name) are reported in `report.skippedManagedCalls`, not invented.
   - `toStudioProject` dispatches on bundle shape. `ReaOutputError` moved to `errors.ts` (still exported).
   - New file helpers in `@rea-studio/rea-adapter/file`: `checkManagedArtifactFile`, `managedProjectionInput`, `adaptManagedFiles`, `reaErrorMessage`. They keep REA JSON interpretation inside the adapter.
5. **Web:**
   - New kind metadata, display names and inspector facts. `native-import` is in the boundary family, like IPC.
   - Sidebar categories; empty Source/Files tabs hidden for .NET.
   - `/explore/tiny-dotnet` demo. Landing copy now says "See how an app is put together" and lists .NET.
   - `/open` accepts `dotnet` projects and recognizes a raw .NET bundle.
   - **Overview cap of 250 nodes** by `KIND_ORDER`, with a "N more parts not drawn" note. Big .NET programs have thousands of methods.
6. **Ask:** `nodeName` / search cover the new kinds.
7. **CLI:**
   - `rea-studio analyze Program.exe|.dll` runs the 3 managed inspections, then the projection.
   - A native exe is refused with a clear reason ("native program, not .NET … needs Ghidra").
   - When REA fails, the CLI now shows REA's own error message.

## Added later the same night: websites
8. **Website adapter** `packages/rea-adapter/src/web.ts` for REA's `analyze_web_bundle` (not an application graph):
   - The page becomes the root file (label = URL). Each captured script becomes a `file` (path on the origin; inline `<script>` blocks are `(inline script N)`).
   - Routes and endpoint candidates are `endpoint` nodes with `calls` from their script, at source locations.
   - Framework/bundler fingerprints (Next.js, React, webpack) are `external-module` nodes with **inferred** `imports` carrying REA's confidence.
   - Project id = the hex of REA's evidence id (a website has no file digest).
   - Schema: `appKind` + `'web'`, `format` + `'url'` (part of the same proposal).
   - Findings: `imports` and `endpoints`.
9. **CLI** `rea-studio analyze https://…` (`apps/cli/src/browser.ts`):
   - Chrome or Chromium headless with a throwaway profile and `--remote-debugging-address=127.0.0.1`. The port is read from `DevToolsActivePort`.
   - Waits for the page, runs `analyze-web-bundle`, then always kills Chrome and deletes the profile. `CHROME_PATH` overrides the browser.
   - Never Edge (it signs fresh profiles into the Windows account).
10. **Explorer:**
    - Website label; the root shows its URL.
    - The overview falls back to files + what they use when an app has none of the architectural kinds. Websites otherwise had an empty overview.
    - Demo `/explore/reaforweb-site`.
11. Tests:
    - adapter `web.test.ts` (6) on the real capture of this site;
    - CLI test that serves a tiny page from 127.0.0.1 inside the test and analyzes it with real Chrome (skipped without Chrome): 3 files and the `/api/items` fetch;
    - CLI on the dev site: 87 nodes, 92 links, 25 s, no leftover Chrome processes or profiles.

## Not done / known issues
- **Uploads:** the worker container still runs only `analyze-javascript-application` on `.asar`/directory. Proposal for Codex (worker owner):
  - Accept `.exe`/`.dll` up to the same size limits.
  - Run the 3 `inspect-managed-*` commands, then `project-managed-application-graph`, all inside the same `--network=none` container.
  - Bundle the outputs and adapt them with `adaptManagedFiles`.
  - Keep `checkManagedArtifactFile` as the gate, so native PEs fail fast with the readable message.
- **Android:** needs the jadx-headless-mcp 0.7.1 JAR (human approval to download). Its bridge (`addJavascriptInterface`) maps onto the existing bridge-api UI.
- **Native .exe:** needs Ghidra 12.1.x + Java 21 in a separate worker image (human approval to download, about 1 GB).
- **Websites:** needs a capture sandbox with origin-restricted egress (SSRF protection); design in `docs/targets.md`. REA's bundle output needs its own small adapter (not written yet).
- External call targets have member names only (`WriteAllText`, not `System.IO.File.WriteAllText`). REA 6.4.0 doesn't resolve TypeRefs. Worth an upstream REA issue.
- REA marks the tiny sample's members inspection `partial`, so the banner shows "partial analysis". That's honest pass-through.
- Browser automation caveat: Edge implicitly signed a fresh scratch profile into the human's Windows account during research. I killed it within a minute and deleted the profile, then switched to Chrome with a scratch profile.
