# T045 — Readable overview for big programs (claude)

**Branch:** `claude/T045-program-overview` (from main `367f235`)
**Status:** review

## Problem (seen on the live site)
`/explore/jq` opened as an unreadable picture. When a project has more than 250 overview parts, the
overview kept the first 250 by kind order. Imports rank ahead of functions, so jq got all 214 imports and
only 36 functions. Most of their calls led outside the drawn set, which left a tangle plus a grid of
disconnected import boxes. Any big .NET program would do the same with methods.

## What changed
- **New `apps/web/lib/entry-tree.ts`:**
  - `isEntryNode()`: a native function flagged `entryPoint` or named `main`/`_main`/`wmain`, a .NET method
    flagged `entryPoint`, or an Android launcher component.
  - `entryTree(nodes, outgoing, candidates, limit)`: breadth-first along outgoing non-containment links from
    the entry points, within the overview's candidates, up to `limit`. Callees that link onward come before
    leaves, so the tree goes deeper than the first level. Returns null when there's no entry point or
    nothing it links to.
  - It's a drawing choice only. No findings or evidence change.
  - It has no runtime relative imports, so Node's type-stripping tests can import it. `graph-view.ts` itself
    can't be imported there because of its extensionless `./project` import.
- **`apps/web/lib/graph-view.ts`:** above `OVERVIEW_LIMIT` (250), the overview is the entry tree with
  `ENTRY_TREE_LIMIT = 40` nodes. I tried 100, but it zoomed out to an unreadable column. GitHub Desktop's
  readable overview draws 36. Without an entry point, the old kind-order fallback still applies.
  `ViewGraph.basis` says how the view was chosen.
- **`apps/web/components/GraphPane.tsx`:** the meta line shows the basis, e.g. "40 nodes · 50 links ·
  calls from the entry point · 1080 more parts not drawn (use search or the findings list)".
- **Unchanged:** every demo with 250 overview parts or fewer, which is all except jq: GitHub Desktop 36,
  Binary Eye 215, the tiny samples.

## How to verify
- `npm test -w @rea-studio/web`: **27/27** (3 new, in `tests/entry-tree.test.mjs`, on the real jq 1.8.2 fixture):
  - The limit-100 tree has exactly 100 nodes and its root is `entry`. Every non-root node is called by a drawn
    node, and the tree reaches past the entry's own callees.
  - Without an entry point, the result is null.
  - `isEntryNode` recognizes `Main` (tiny .NET), `main`/`_main`/`wmain` (not `mainloop` or `FUN_…`) and Android launchers.
- Web typecheck clean. `next build` passes.
- **Visual check** (headless Chrome at 1400×900 on `next dev`):
  - Before: the live site's `/explore/jq` showed a tangle plus an import grid.
  - After: one connected left-to-right tree: `entry` → the C runtime's main (`FUN_140001ab0`) → its CRT imports
    and the functions it calls, and deeper.
  - The images are outside Git: `launch-verification/T045-jq-before.png` and `T045-jq-after.png`.

## Not done / known issues
- Windows jq is stripped, so the tree starts in C runtime startup rather than jq's own `main`. The macOS build
  (T035) names `entry` = `main` and would start in jq's code.
- The rest of the program is still reachable through search, the findings list and double-click neighborhoods,
  as before.

## Interface changes or questions for the other agent / human
- None outside the web app. `ViewGraph` gains an optional `basis` field (web-internal).
