## What changed

- Added the fifth workspace, `packages/pipeline`, with browser-safe contracts,
  private object storage, upload control, and trusted queue orchestration.
- Added the upload form, job progress page, and authenticated upload/job/result
  APIs. The existing explorer renders the resulting `StudioProject`; the schema
  and adapter semantics are unchanged.
- Added streaming local storage and an R2 implementation with ten-minute signed
  PUT URLs. The trusted worker verifies actual size and SHA-256 before analysis
  or cache reuse. There is no public hash lookup. Upload hashes and REA project
  IDs remain separate.
- Added Redis/BullMQ orchestration, globally serial analysis, idempotent queueing,
  bounded progress, generic failures, and a separate host queue entry point that
  calls the existing Docker runner. Storage/queue credentials never enter the
  analysis container; the uploaded app is never executed.
- Results are compressed and private. Per-job bearer tokens are stored only in
  browser sessionStorage, with server-side token hashes and 24-hour access.
  R2 mode requires HTTPS and a private beta access key. Admission is capped at
  100 upload tickets per UTC day.
- Raw uploads and private staging are removed before successful acknowledgement.
  Startup/hourly expiry sweeps cover abandoned data. An R2 lifecycle rule is the
  independent backstop for late reuse of a still-valid PUT URL.
- Added `npm run dev:uploads`, environment examples, setup documentation, storage
  and queue tests, and Redis verification in the existing GitHub workflow.

## How to verify

From this branch, with Docker Desktop running:

```powershell
npm ci --ignore-scripts
npm run typecheck
npm test -w @rea-studio/rea-adapter
npm test -w @rea-studio/worker
npm test -w @rea-studio/pipeline
npm run dev:uploads
```

Open `http://localhost:3104/upload`. The helper builds the production app and
analysis image, starts loopback-only Redis on port 6380 with persistent storage,
and runs the trusted queue worker and web app. Ctrl+C stops those services.
Ports can be changed with `UPLOAD_DEV_PORT` and `UPLOAD_REDIS_PORT`.

In a separate terminal while the helper runs:

```powershell
$env:PIPELINE_TEST_REDIS_URL='redis://127.0.0.1:6380'
npm run test:integration -w @rea-studio/pipeline
$env:PIPELINE_TEST_ORIGIN='http://localhost:3104'
npm run test:http -w @rea-studio/pipeline
npm run test:docker -w @rea-studio/worker
```

- All five workspace typechecks and the full production build pass.

## Not done / known issues

- No Cloudflare bucket, credentials, hosted Redis, or deployment was created.
  The user has a Cloudflare account but has not confirmed an R2 bucket. R2 signing
  has an offline test; live PUT/CORS/read/delete/lifecycle still need verification
  when an account is connected. See `docs/uploads.md` for the exact setup.
- This is a private beta with ASAR uploads only. Anonymous public admission,
  user accounts, worker scaling, result retention, and user-facing queued-job
  cancellation are outside this task. Browser cancellation covers preparation
  and uploading before queue submission.
- The actual ASAR fixture produces seven REA `asar-entry` nodes that the current
  adapter reports explicitly as analysis gaps. They are packaging metadata;
  the observed processes/IPC/window/bridge findings still render. Claude should
  examine an ASAR fixture before extending the mapping; no guessed schema or
  adapter mapping was introduced here.
- A worker crash leaves raw/staging cleanup to expiry sweeps; the existing
  container deadline remains active. Recovery of a stopped orphan container
  after host-process death is not added by T007.
- Normalized caches remain private without automatic result expiry. Bump the
  cache revision when analysis settings or adapter semantics change.
