# T024 — Analysis worker for programs: .NET and native with Ghidra (claude)

**Branch:** `claude/T024-native-worker`
- **Stacked on** `claude/T021-beyond-electron` (26d2c48), because it needs T021's native adapter and collector. Merge T021 first.

**Status:** review. Codex owns the worker, so please review the sandbox parts closely.

The human approved it: "YES add ghidra to the analysis server". The worker can now analyze `.exe`/`.dll` files in Docker, with the same sandbox as Electron jobs.

## What changed
1. **`apps/worker/Dockerfile.native`:** a second image, `rea-studio-worker-native:rea-6.4.0`, built `FROM` the standard image. It adds:
   - **JDK 21:** Temurin 21.0.12.1, `eclipse-temurin:21-jdk-noble` pinned by digest, without `jmods`.
   - **Ghidra 12.1.4:** fetched with `ADD --checksum=sha256:ddac49f9…`, the checksum I verified against the release earlier. Windows/macOS binaries, docs and IDE extensions are removed.
   - **jadx-headless-mcp 0.7.1:** `ADD --checksum` with the SHA-256 REA itself pins, ready for Android.
   - Environment: `JAVA_HOME`, `GHIDRA_INSTALL_DIR`, `REA_JADX_MCP_JAR`.
   - Size: 2.17 GB. The build took 145 s here.
2. **Target kinds** `exe` / `dll`:
   - `preflight.ts`: the target must be one ordinary file within `maxInputBytes`, starting with `MZ`.
   - Host (`run-analysis.ts`): accepts `.exe`/`.dll` and mounts the file read-only at `/input/target.exe|dll`.
   - `containerArgs` takes an `image` argument. Only the two known images are accepted.
   - The sandbox flags are **unchanged** for both images. Measured with the existing limits:
     - `tiny-notes.exe`: 54 PIDs, about 700 MiB.
     - `notepad.exe`: 52 PIDs, about 940 MiB, 245 s.
3. **Image choice:** `AnalysisOptions.native` (operator setting).
   - Worker CLI: `--native`. Queue: `REA_NATIVE_WORKER=0|1`, validated.
   - Directories and ASARs always use the standard image.
4. **Container entrypoint:**
   - The REA spawn is factored into `runRea`. The JS path is unchanged in behavior.
   - **Programs:**
     - Run `inspect-managed-artifact` first.
     - If it's .NET: run the other two inspections, then the projection, then `adaptManagedFiles`.
     - If it's native and Ghidra is configured: `collectNativeBundle`, from the adapter's `native-session`, over `rea --mcp`. Then the bundle is size-checked and passed to `adaptReaFile`.
     - If it's native without Ghidra: `invalid_input`, with "Native programs need the native analysis worker (Ghidra)."
   - The entrypoint emits `rea_progress` lines (phases `inspect`, `managed`, `native`).
   - Ghidra's JVM heap is `GHIDRA_HEADLESS_MAXMEM = heapMb`.
5. **Tests:**
   - Worker unit tests: 36 (+3):
     - exe/dll mounts and image selection, with unknown images rejected;
     - MZ/size preflight;
     - the env setting.
   - Real Docker: **9 pass** (+2):
     - .NET in the standard image (3 native imports), with a native program refused as `invalid_input` and no output;
     - Ghidra in the native image: 49 functions and the URL endpoint. This one skips if the image isn't built.
   - Worker vs local CLI on `tiny-notes.exe`: identical projects (same id, 96 nodes, 136 links). Linux Ghidra in the sandbox gives the same result as Windows Ghidra locally.

## How to verify
```sh
npm ci && npm run build:packages && npm run build -w @rea-studio/pipeline && npm run build -w @rea-studio/worker
npm test -w @rea-studio/worker
docker build -f apps/worker/Dockerfile -t rea-studio-worker:rea-6.4.0 .
docker build -f apps/worker/Dockerfile.native -t rea-studio-worker-native:rea-6.4.0 .
npm run test:docker -w @rea-studio/worker
node apps/worker/dist/cli.js fixtures/sample-apps/tiny-native/tiny-notes.exe <out> --native
```
Note: I rebuilt the local `rea-studio-worker:rea-6.4.0` tag from this branch. It's a superset; ASAR/directory jobs are unchanged. Codex's `rea-studio-worker:integration-review` tag is untouched.

## Not done / known issues
- **Uploads:** the pipeline (T007) still accepts `.asar` only: validation, `uploads/<id>.asar` keys, the cleanup regexes, the job name and the error copy. Allowing `.exe`/`.dll` there is the next step. The worker side is ready.
- **Speed on big programs:** one `procedure_callees` MCP call per function, about 0.2 s each. REA's `get_call_graph` only walks from one root, so it doesn't replace this. Possible fixes:
  - a function cap that publishes partial coverage;
  - a REA upstream request for a whole-program callee export.
- **CI:** `.github/workflows/worker.yml` doesn't build the native image (2.2 GB), so its Docker test skips there. Add a job if you want it covered.
- The native image is about 2.2 GB. Ghidra's Linux-only processors could be trimmed further.
